# SARAS ERP v3 — Implementation Plan

**Spec:** `docs/specs/2026-04-29-erp-v3-design.md`
**Target:** new repo `saras-erp-v3`, new Vercel project, new Supabase project
**Branch:** `main` from day 1 (no feature branching for solo work)
**Total estimate:** 8 weeks single-developer focused work

---

## Critical path

```
Phase 0 (foundations) → Phase 1 (Dashboard) → Phase 2 (Masters) →
  Phase 3 (Orders) → Phase 16 (POS) → Phase 18 (verdict)
```

The remaining phases (4–15, 17) parallelise after Phase 2 lands the master pattern. Sequential build-and-compare per design Q6 = A keeps the pipeline single-stream until we've validated the shell ergonomics — then we can fan out.

Every table gets the universal infrastructure cols (design §7.1): created_at/updated_at/created_by/updated_by/deleted_at/idempotency_key + audit trigger + RLS + realtime.

### 2.2 Migration script extension

`tools/migrate-v2-to-v3.ts` extended with logic for each master:

- Customers: split `shipping_addresses` jsonb → multiple `customer_addresses` rows
- Machine_types: split `serial_numbers` jsonb → multiple `machine_units` rows
- Junction tables created from `compatible_*_ids` jsonb arrays
- `created_by` filled from `user_id`

### 2.3 Master page pattern

One generic page component handles all 22 masters:

`src/modules/masters/MasterPage.tsx` takes a config:

```ts
interface MasterConfig<T> {
  tableName: string
  displayName: string
  schema: ZodSchema<T>           // form validation
  columns: ColumnDef<T>[]        // list display
  contextRender?: (row: T) => ReactNode  // right-panel content
  searchFields: (keyof T)[]
}
```

Per-master configs live in `src/modules/masters/configs/`:

- `customers.ts`, `products.ts`, `suppliers.ts`, etc — one config per entity

The page renders:

- Rail: groups/categories filter + search
- Centre: list of records (DataTable for <500 rows; DataGrid virtualized for products at 2310)
- Context: selected record details + recent activity (when applicable)

Edit happens in a Drawer, never a new page. Photo Wizard pattern (from POS) reused for product/customer/operator photo upload.

## Risk register

| Risk | Mitigation |
|---|---|
| Operator (you) doesn't have time for 16 Comparison Days | Each Comparison Day is 1-2 hrs; can be deferred per-module without blocking the next phase if module's v3 implementation passes a self-test against the standard script |
| v3 design mistakes baked into 16 modules before discovery | Phase Step 4 comparison gate after EACH module catches issues before the next phase compounds them |
| TypeScript strict mode causes early friction | Tolerate it; the type errors are exactly what saves us from v2 lesson #12 (envelope drift) |
| Imported primitives have hidden v2-specific assumptions | Phase 0.3 includes porting the v2 unit tests for these files; any failure surfaces immediately |
| Supabase advisor false positives | Already lived through this in v2 POS Phase 13; use `execute_sql` to verify directly when advisor cache is suspicious |
| Switch pill breaks if route paths diverge | Symmetric routes enforced as a v3 invariant; if v3 needs a new route v2 doesn't have, switch-pill falls back to "/" on the other app |
| Bundle bloat creeps in | CI fails build if main bundle exceeds 350KB gzip; phase 17 audit catches before launch |
| Migration script drifts from v2 schema as v2 picks up new orders | Re-run the script weekly during comparison; idempotent on `id` so it's a no-op on already-imported rows |
| 8-week estimate overruns | Each phase is its own commit; nothing prevents shipping v3 partial (e.g. only Phases 0-9) and starting comparison early |

## What this plan does NOT specify

These get their own sub-specs (one per module Phase Step 1, written before the build of that phase begins):

- Per-module exact realtime subscription topics
- Per-module empty-state copy
- Per-module keyboard shortcut overrides (where they differ from the universal F-keys)
- Reports module's specific report set + chart library choice (decided in Phase 15.1)

- All 19 phase outlines (0–18) have files-touched, acceptance criteria, and dependencies

- Each transactional module has its 3-panel layout sketched
- Each Comparison Day gate is explicit
- Total estimate fits in 8 weeks ± 1 week for solo focused work
